# DENCAL

一般病院の院内サーバー・PCでの動作を想定した電子カルテの試作です。機能を一つずつ実装しながら画面とデータ構造を調整します。

**実務利用前の試作です。架空データのみで確認してください。**

外来カルテ診療、確定診療録の検索、受付・会計算定、バックアップ・保存性、安全管理・監査証跡の画面があります。

## 院内配備の構成例

[院内配備の構成図](docs/on-premises-deployment.md)に、テナント診療所のPC1台構成、医師・会計担当のPC2台構成、受付・診察室・処置室の複数PC構成を掲載しています。専用院内サーバー、院内LAN、バックアップ、停電時の給電範囲を確認できます。

## 起動

Node.js 22.13以降と Python 3.10以降（SQLite 3.31以降）を使用します。

```sh
npm ci
npm run db:init
npm run dev
```

Viteが表示するローカルURLを開き、DB初期化時に端末へ表示された職員IDとパスワードでログインします。パスワードはアカウントごとに生成され、初期化時にのみ表示されます。

| 職員ID | 最低職種 | この職種から利用できる操作 |
| --- | --- | --- |
| `demo-reception` | 受付 | 外来カルテ閲覧、患者登録、受付・会計デモ |
| `demo-nurse` | 看護師 | バイタル・アレルギー登録デモ |
| `demo-physician` | 医師 | SOAP編集・確定、処方・検査指示、紹介状のテキスト出力 |
| `demo-admin` | 管理者 | 公式マスターの取り込み、全カルテのデモJSON出力、バックアップ・安全管理・監査デモ |

権限は **管理者 ＞ 医師 ＞ 看護師 ＞ 受付** の順に下位の操作を継承します。職種を変える場合はログアウトして別の職員IDでログインします。セッションは30分で失効し、離席操作でも終了します。

サーバーは患者一覧、個別カルテ、更新、確定、出力のリクエストごとに職種と対象患者の担当部署を確認します。管理者は全部署、その他の職種は所属部署の患者にアクセスできます。所属が未設定の職員には患者へのアクセス権がありません。デモの受付・看護師・医師は総合診療科に所属します。新規患者は登録者の所属部署に割り当てられ、所属未設定の管理者が登録する場合は総合診療科に割り当てられます。

二要素認証（2FA）は、実務利用に向けた開発の最終段階で実装する予定です。開発中は動作確認のためにログインとログアウトを頻繁に繰り返すため、認証手順が煩雑になることを避けるためです。

`db:init` は `data/dencal.sqlite3` を新規作成し、既存DBの上書きは拒否します。スキーマバージョン2〜5のDBは、最初のAPIリクエストで既存のデータを保持したままバージョン6へ移行します。診療用テーブルと初期サンプルは、この移行時に作成します。別のファイルを新規作成する場合は、たとえば `npm run db:init -- data/auth-demo.sqlite3` で作成し、サーバー起動時の環境変数 `DENCAL_DB` に同じパスを指定してください。

職員認証・所属部署・セッション・公式マスター・診療録をSQLiteに保存します。診療データの試算やバックアップ画面は試作です。

## 診療録の保存・確定・訂正

1. 医師または管理者で患者を開き、SOAPを入力して **下書きを保存** を押します。
2. **診療録を確定** を押すと、SOAP・傷病名・処方・検査オーダの確定版を作成し、最終入力者・確定者・日時を記録します。
3. 確定後は理由を入力して **訂正を開始** します。訂正の入力を保存し、**訂正版を確定** すると、新しい版が履歴に追加されます。

保存した下書きと確定版は再起動後も残ります。未保存のSOAP入力は画面内に保持されます。同じ下書きを別画面で更新した場合、古い版を基にした保存・確定は拒否されます。確定版はSQLiteのトリガーで上書きと削除を拒否し、参照時に版ごとのSHA-256を検証します。

## 確定診療録の検索・印刷

1. 上部の **確定診療録** を開きます。患者番号・氏名・フリガナ、受診日の範囲を指定して検索できます。
2. 結果から確定版を選びます。訂正前の版も表示でき、閲覧時に版のハッシュを検証します。
3. 医師・管理者は **HTMLを保存** または **印刷用に開く** を選べます。ブラウザーの印刷画面からA4印刷やPDF保存ができます。

HTMLはUTF-8で、ネット接続やDENCALなしでも開けます。出力内容は患者・受診の識別情報、確定時のSOAP・傷病名・処方・検査オーダ、確定者・日時・訂正理由、版のSHA-256です。閲覧・出力の権限はサーバーが職種と担当部署に基づいて確認し、選択した版を監査記録に残します。

## 電子署名・タイムスタンプ

署名を有効にした環境では、**診療録を確定** または **訂正版を確定** を押すと、職員に紐付けたX.509証明書で確定データにCMS分離署名を付け、署名に対するRFC 3161タイムスタンプを取得します。TSA（時刻認証局）に送るのは署名のSHA-256、nonceなどを含むタイムスタンプ要求です。確定データ、秘密鍵、患者情報は送信しません。署名・タイムスタンプの検証が成功した場合に限り、確定版と証跡を一緒にSQLiteへ保存します。

OpenSSL 3.xの `openssl` を実行できるサーバーで、アプリのディレクトリ外に次のような設定ファイルを用意し、環境変数 `DENCAL_SIGNING_CONFIG` にそのファイルの絶対パスを指定して再起動します。

```json
{
  "signerCaFile": "signer-trust.pem",
  "tsaCaFile": "tsa-trust.pem",
  "tsaUrl": "https://tsa.example.invalid/timestamp",
  "signers": {
    "demo-physician": {
      "certificate": "physician.pem",
      "key": "physician.key",
      "chain": "physician-intermediates.pem"
    }
  }
}
```

相対パスは設定ファイルのあるディレクトリを基準に解決します。職員ごとに署名用の証明書と対応するPEM秘密鍵を設定します。中間証明書が不要なら `chain` は省略できます。TSAがポリシーOIDや認証を指定する場合は、それぞれ `tsaPolicy` と `tsaAuthorizationFile` を設定します。認証ファイルにはAuthorizationヘッダーの値を1行で置きます。秘密鍵・認証ファイルはアプリのディレクトリ外に置き、署名プロセスの実行アカウントにアクセスを限定してください。サーバー時刻とTSA時刻の差が5分を超える応答は拒否します。

確定後は **確定診療録 → 対象版 → 電子署名・タイムスタンプを検証** を選びます。証明書チェーンをタイムスタンプ時点で検証し、確定データ・署名・タイムスタンプの対応を確認します。SQLiteに保存した証跡を使うため、検証時のTSA接続は不要です。復元先で検証だけを行う場合は、設定に `signerCaFile` と `tsaCaFile` を指定します。証明書の更新時も、既存の版を検証するために必要な信頼ルートを保管してください。

設定のない新規デモDBでは従来どおり署名なしで確定できます。署名済み版のあるDBでは、設定を外した状態での新たな確定を拒否します。既存の確定版は署名なしのまま保持します。署名対象はSQLiteの確定データです。印刷用HTMLには証跡情報を表示します。HPKIカード・クラウド署名、CRL/OCSPによる失効確認、長期署名の更新は今後の実装対象です。[厚労省ガイドライン第7.0版 システム運用編](https://www.mhlw.go.jp/content/10808000/001716295.pdf)

## 診療録の保存・移行・復元

診療録、訂正履歴、参照に必要な情報は自動削除しません。診療録の保存期間は、医師法第24条と、保険診療では診療完結日から5年間とする療養担当規則第9条を参照してください。保存先や保存期間を含む運用は施設で管理します。[厚労省の法令資料](https://www.mhlw.go.jp/content/10601000/001230827.pdf)

サーバー側の担当者が、DENCALのディレクトリで次のコマンドを実行します。元のDBが既定のパスと異なる場合は、書き出し時も `DENCAL_DB` に元のパスを指定します。DBが旧版の場合はアプリを起動し、ログイン画面を開いて先にスキーマを更新します。

```sh
npm run records:export -- data/clinical-archive.sqlite3
npm run records:verify -- data/clinical-archive.sqlite3
npm run records:restore -- data/clinical-archive.sqlite3 data/clinical-restored.sqlite3
```

書き出しと復元はSQLiteの整合性・外部キー・確定版のハッシュを検査し、検証を通過したDBを新しいファイルとして作成します。既存ファイルは上書きしません。保存先にはハードリンクを作成できるローカルファイルシステムを指定し、外部媒体へ移す場合は検証済みファイルをコピーしてください。復元先を `DENCAL_DB` に指定して起動し、元の職員アカウントでログインして版を確認します。ログインセッションは引き継ぎません。

SQLiteファイルには下書き、確定版、職員の認証情報を含みます。アクセス制限した領域に保存してください。暗号化、世代管理、隔離保管は施設側の運用で整備します。他システムとのFHIR等によるデータ交換は今後の実装対象です。

## マスターと外部連携

[RECEPT連携の設計計画](docs/recept-integration.md)では、確定カルテ・実施記録から請求候補を送る範囲と実装順序をまとめています。

1. 管理者でログインし、上部の **マスター管理** を開きます。
2. 厚生労働省の配布ページから令和8年度版の全件マスターを取得します。ZIPを解凍し、CSV・TXTを元のファイル名で一つずつ取り込みます。
3. 医師または管理者で **外来カルテ診療** を開き、登録傷病名・処方オーダ・検査オーダから候補を検索して追加します。

| 対象 | 展開後のファイル名の例 | 公式配布元 |
| --- | --- | --- |
| 傷病名 | `b_20260601.txt` | [厚労省 傷病名・修飾語マスター](https://shinryohoshu.mhlw.go.jp/shinryohoshu/standardMenu/doStandardMasterBz/) |
| 医薬品 | `y_20261013.csv` | [厚労省 基本マスター全件ダウンロード](https://shinryohoshu.mhlw.go.jp/shinryohoshu/downloadMenu/) |
| 医科診療行為 | `s_20261102.csv` | [厚労省 基本マスター全件ダウンロード](https://shinryohoshu.mhlw.go.jp/shinryohoshu/downloadMenu/) |

取り込み・検索はDENCAL自身のAPIとSQLiteで完結します。マスターは利用者が公式サイトから取得します。検索は日本時間の当日に利用できる最新の取込版を使います。処方候補は内用薬・外用薬、検査候補は入院専用を除く医科診療行為マスターの検査・病理診断の項目です。傷病名・医薬品のレセ電算コードと、医薬品の薬価基準収載医薬品コードを区別して扱います。[マスターファイル仕様説明書](https://www.hpdx.or.jp/seikyushiharai/tensuhyo/kihonmasta/)

公式マスターは名称・規格の選択に使います。処方の用法・用量・日数は入力者が指定します。処方の照合は薬剤名と同一薬剤の重複候補に限ります。禁忌・相互作用・腎機能別用量や、検査点数の正式な算定は未実装です。選択したカルテ明細と選択時のマスター参照情報はSQLiteに保存され、確定時に版の一部として固定されます。

共通算定モジュールは利用しません。医療機関名義での契約・接続手続きが必要なため、試作段階では同モジュールとオンライン資格確認に接続していません。診療報酬の計算は将来、独自の算定機能と連携して行う設計です。画面の試算値は動作確認用です。

## 診療行為の実施記録とRECEPT連携

1. 管理者が **マスター管理** から医科診療行為マスターを取り込みます。スキーマ移行前に取り込んだ版を使う場合は同じ公式ファイルを再取込します。既存版を維持したまま外来・固定点数の対象情報を補完します。
2. **外来カルテ診療 → 実施記録・RECEPT連携** で、看護師以上が実施日・行為・数量を登録します。単位はマスターを使い、空欄の場合は「回」を使います。誤登録は理由を入力して取り消し、正しい実施を登録します。
3. 医師・管理者はカルテを確定し、**送信待ちデータを作成** を押します。確定版の傷病名と実施記録が対象です。初回は少なくとも1件の有効な実施記録が必要で、検査オーダだけでは送信待ちを作成できません。傷病名のコードと出典を公式マスターで確認できない場合は、カルテ側で確認・訂正します。
4. 送信履歴から連携版ごとの **送信内容を確認** を開き、**RECEPTへ送信** を押します。訂正・受診取消は理由を入力し、新しい連携版として保存します。送信は先行版から行います。

送信待ちデータ・送信履歴はSQLiteに保存します。再送では同じ連携IDと同じJSONバイト列を使い、受領結果のIDと本文ハッシュが一致した場合に保存します。送信結果が返らない場合も診療録と実施記録は残ります。送信中にサーバーが停止した場合は、最大20秒の送信中表示が解消した後に再送できます。

送信先を利用する場合は、DENCALサーバーの環境変数 `DENCAL_RECEPT_URL` に `http://127.0.0.1:<ポート>` の形式でRECEPTの接続先を設定し、`DENCAL_RECEPT_TOKEN` に受信側と合意したトークンを設定します。施設IDとDBごとの送信元IDは画面に表示されます。設定がなくても、実施登録と送信待ちデータの作成は利用できます。受信・照合の実装はRECEPT側の後続工程です。

## 保守・運用支援

保守・運用支援が必要な場合は、別途契約により有償で対応します。対応範囲と費用は個別の契約で定めます。

## ライセンス方針

将来、医療機関の直接利用は無料とし、業者による流用販売にはレベニューシェアを基本とするライセンス料を設定する方針です。正式条件は別途定めます。
