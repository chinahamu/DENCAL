# DENCAL

DENCALは、一般病院の外来・入院業務を対象とする、院内サーバーまたは院内PCで動作する電子カルテの開発プロジェクトです。[RECEPT](https://github.com/chinahamu/RECEPT) と連携し、患者台帳、受付、診療・看護記録、処方・検査の指示と実施、入退院・転棟の管理を段階的に実装します。

> [!IMPORTANT]
> **開発初期のため、現在は実務利用できません。** 動作確認には架空データを使ってください。実患者の情報を入力したり、実際の診療・会計・保険請求に使用したりしないでください。

## 開発方針

機能を一つずつ実装し、架空データで実際に画面を操作しながら、現場の業務に合わせて調整します。初期は外来の基本業務から着手し、入院・病棟業務へ段階的に広げます。

厚生労働省の「医療情報システムの安全管理に関するガイドライン 第7.0版」を設計の基準とし、要件と機能の対応、実装状況、確認結果を段階的に公開します。現時点の位置付けは開発初期です。[厚生労働省のガイドライン](https://www.mhlw.go.jp/stf/shingi/0000516275_00006.html)

[ガイドラインと機能の対応表・実装状況](docs/mhlw-guideline-mapping.md)

## 単体PCで試作版を起動する

診療録のSOAP化に伴い、DBはスキーマ版11を使用します。旧試作DBを使っていた場合は、起動と職員登録の両方で `--db data/dencal-soap.sqlite3` など新しいファイルを指定してください。

Python 3.11以上が必要です。追加パッケージは不要です。リポジトリのルートで次を実行します。Windowsでは `py -3`、macOS・Linuxでは `python3` を使います。

```powershell
py -3 prototype/server.py
```

```bash
python3 prototype/server.py
```

1. 初回は下記の手順で架空の職員を登録します。同じPCのブラウザで [試作画面](http://127.0.0.1:8765/) を開いてログインし、データベースの「利用可能」を確認します。接続は同じPC内に限定します。
2. 初回起動時に、起動ディレクトリの `data/dencal.sqlite3` を自動作成します。ターミナルで Ctrl+C を押して停止します。
3. 同じディレクトリで再度起動します。画面に表示される初期化日時が初回と同じなら、既存DBを利用できています。

DBの保存場所は `--db`、ポートは `--port` で変更できます。たとえば `py -3 prototype/server.py --db data/test.sqlite3 --port 8766` で起動した場合は、同じPCでポート8766を開きます。DBパスがディレクトリを指している場合などは、パスと原因をターミナルに表示して起動を中止します。

### 架空の職員を登録・無効化する

別のターミナルで同じディレクトリを開き、次を実行します。Windowsでは `python3` を `py -3` に置き換えます。

```bash
python3 prototype/server.py --add-staff demo-a --role reception
```

試作用のパスワードを入力します。15文字以上、UTF-8で256バイト以下です。DBに保存するのはソルトとハッシュです。既定の職員やパスワードはありません。起動時に `--db` を指定した場合は、職員の登録・無効化にも同じパスを指定します。

職員ID `demo-a` でログイン後、画面上の「ログアウト」でそのセッションを終了できます。試作のセッションは発行から30分で失効します。同じ試作サーバーで60秒の間にログイン失敗が10回に達した場合は、その時間枠が終わるまでログイン試行を制限します。

```bash
python3 prototype/server.py --disable-staff demo-a
```

この操作後は `demo-a` の再ログインを拒否し、別ブラウザを含む既存セッションも失効します。

### 職種別の操作権限を確認する

権限は **管理者 ＞ 医師 ＞ 看護師 ＞ 受付** の順です。上位の職種は下位の操作をすべて利用でき、メニューにも表示されます。

| `--role` | 最低職種 | この段階で追加される操作 |
| --- | --- | --- |
| `reception` | 受付 | 患者登録・検索・確認、外来受付の登録・一覧・受診情報の閲覧、`/trial/reception-preview` |
| `nurse` | 看護師 | `/trial/nursing-preview` |
| `physician` | 医師 | 診療録の保存・確定・訂正・履歴の閲覧、処方指示の登録・閲覧、`/trial/consultation-preview` |
| `admin` | 管理者 | 監査ログの閲覧、`/trial/administration-preview` |

既存の職員にはローカルのターミナルから職種を割り当てます。役割を指定せず登録した職員は「未割当」となり、ログインはできますが試作用操作は利用できません。

```bash
python3 prototype/server.py --set-staff-role demo-a --role physician
```

職種の変更は、ログイン中の職員にも次のリクエストから適用されます。各画面の「試行する」は対応する操作APIを呼び、成功すると確認用のJSONを返します。例えば診察の試行は `POST /api/trial/consultation-preview` です。権限のない職種では、画面のURLを直接開く場合も、操作APIを直接呼ぶ場合も HTTP 403 になります。

### 架空の操作の監査ログを確認する

1. 医師と管理者の架空アカウントを、それぞれ `--role physician` と `--role admin` で登録します。
2. 医師でログインし、「診察の試行」から「試行する」を押します。受付アカウントで同じAPIに同一オリジンのPOSTを送ると、権限不足で拒否されます。
3. 管理者のメニューから [監査ログ](http://127.0.0.1:8765/audit) を開きます。架空の対象ID `demo-patient-001`、操作者ID、時刻（UTC）、操作、結果を照合できます。

管理者は `GET /api/audit` でも直近100件を取得できます。一般職員は一覧・APIのどちらも閲覧できません。画面とAPIは参照専用です。試作用操作では識別子と結果だけを記録します。患者機能が追加されたら、同じ記録処理を対象操作に組み込みます。

### 架空の患者を登録する

受付（`reception`）でログインして「患者登録」を開き、架空の氏名と生年月日を入力します。登録すると患者番号が表示されます。同姓同名の別人を登録するときは「別の患者を登録する」から新しいフォームを開きます。

同じ送信を再試行した場合は、同じ患者番号が返ります。管理者の監査ログでは、`patient-register` の成功を患者番号で照合できます。失敗・拒否時は登録操作の識別子を記録します。氏名と生年月日は監査ログに保存しません。

### 架空の患者を検索・確認する

受付（`reception`）でログインし、「患者検索」を開きます。患者番号・氏名・生年月日のいずれかを入力します。患者番号・生年月日は完全一致、氏名は部分一致で検索し、複数項目はすべて一致する患者に絞ります。

結果は最大50件です。患者番号と生年月日で同姓同名の患者を区別し、該当行の「確認」で患者情報を開けます。検索結果に表示した患者と、確認画面を開いた患者は、管理者の監査ログでそれぞれ `patient-search`、`patient-view` として照合できます。検索条件の入力値は監査ログに保存しません。

### 架空の外来受付を登録する

受付（`reception`）で患者を検索し、対象行の「確認」を開きます。患者番号・氏名・生年月日を確認し、診療科（試作では内科・外科）と来院日を指定して「外来受付を登録する」を押します。完了画面に受付番号、患者、診療科、来院日を表示します。

同じフォームの再送では元の受付番号を返します。別の来院を登録する場合は、患者検索から確認画面を開き直してください。管理者は監査ログの `outpatient-check-in` を患者番号で照合できます。

### 診療科別の外来受付一覧を開く

受付以上の職種で「外来受付一覧」を開き、診療科を選びます。試作サーバーのローカル日付を基準に、その診療科の当日分を受診ID順に50件ずつ表示します。

対象行の「開く」で、受診ID、患者番号、氏名、生年月日、診療科、来院日を確認できます。別の日付・診療科の受診IDを送っても、その一覧の受診としては開けません。管理者は `outpatient-list` と `outpatient-visit-view` の監査ログを受診IDで照合できます。

### 診療録の下書きを保存する

医師（`physician`）で当日の外来受付一覧から対象の受診を開き、患者番号・受診IDを確認します。「診療録の下書き」のS・O・A・P欄に架空の内容を入力し、「下書きを保存する」を押します。同じ受診を開き直すと、保存済みの本文が表示されます。

別の画面で先に保存されていた場合は、上書きせずに競合を表示します。未保存の入力を確認し、「最新の下書きを開く」から最新版を読み直してください。管理者は `clinical-note-draft-save` の監査ログを受診IDで照合できます。本文は監査ログに保存しません。

### 診療録を確定する

医師（`physician`）で下書きを保存し、「保存済みの下書きを確定前に確認する」を開きます。患者・受診と保存済み本文を照合し、「この内容で確定する」を押します。確定済み画面には本文、入力者ID、確定者ID、作成日時、確定日時（いずれもUTC）を表示します。確定前に別の版が保存された場合は、最新版の確認からやり直します。確定済みの本文は通常の編集から上書きできません。

入力者は確定した版を最後に保存した職員です。時刻は試作サーバーのシステム時計を使用します。管理者は `clinical-note-finalize-review` と `clinical-note-finalize` の監査ログを受診IDで照合できます。

### 確定済み診療録を訂正する

医師（`physician`）で当日の外来受診を開きます。「確定済み診療録の訂正」に訂正後の本文と理由を入力し、「理由を記録して訂正する」を押します。画面には現行版が表示され、「訂正履歴」から過去の訂正版と確定時の元版を確認できます。各訂正版には訂正者ID・訂正日時（UTC）・理由が残ります。

別の画面で先に訂正が保存されていた場合は、最新版を開き直してください。監査ログの `clinical-note-correct` は受診IDで照合できます。本文と訂正理由は診療録の履歴に保持します。

### 処方指示を登録する

医師（`physician`）で当日の外来受診を開き、患者と受診IDを確認します。「処方指示」に架空の薬剤名・用量・単位・用法・日数を入力して登録します。すべて必須です。受診を開き直すと登録済み指示の内容と「指示済み・実施未記録」の状態を確認できます。

同じ登録フォームを再送しても指示は1件です。管理者は `prescription-order` の監査ログを受診IDで照合できます。

## 診療報酬の算定とオンライン資格確認

### 診療報酬の算定

健康・医療共通算定モジュールの本番利用は、対応レセコンを導入した医療機関を通じて行います。本プロジェクトでは、医療機関名義で契約・利用手続きを進められる連携先を確保できていないため、本番環境に接続できず、同モジュールは利用しません。[厚生労働省の案内](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/iryouhoken/newpage_00016.html)

RECEPTに独自の算定機能を段階的に実装し、対応する診療行為の診療報酬点数と患者負担額を院内で計算できるようにします。

### オンライン資格確認

オンライン資格確認は、連携先の医療機関名義での利用申請と、接続方式に応じた設定が必要です。本プロジェクトでは利用手続きや本番接続に必要な環境を確保できていないため、本番連携は未実装です。[医療機関等向け総合ポータルサイトの案内](https://iryohokenjyoho.service-now.com/csm?id=kb_article_view&sysparm_article=KB0010416)
