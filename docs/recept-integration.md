# RECEPT連携の設計計画

DENCAL側の設計案。確定カルテと実施済みの診療行為から、RECEPTに渡す請求候補を作る。連携API・画面は設計段階。共通の契約 v1、JSON Schema、テストデータは実装済み。

[相手側の設計計画](https://github.com/chinahamu/RECEPT/blob/main/docs/dencal-integration.md)

## DENCAL側の実装範囲

- [確定カルテの保存処理](../server/clinicalStore.ts)は傷病名・処方・検査オーダを版に保持する。[DB定義](../database/schema.sql)には診療行為の実施テーブルがある。実装では実施の登録・取消と、対象行為を取り出す処理を追加する。
- オーダだけの行為は請求候補に含めない。実施記録を元オーダと紐付けられる場合は参照を保持し、カルテの確定後に実施・取消が発生した場合も送信対象を確認できるようにする。
- 確定版番号と実施明細IDを元データへの参照として残す。受診画面で未送信・送信待ち・要確認・反映済みを確認し、送信失敗時は履歴から同一内容を再送できるようにする。
- DENCALの公式マスター取り込みと診療入力用検索は既存どおりDENCAL内で完結させる。RECEPTへの送信・照会は、診療録の保存や確定から独立させる。

## 共通の連携契約（案 v1）

初期対象は同一PCで動作する開発版の外来診療で、架空データを使う。DENCALは確定カルテ・実施記録、RECEPTは請求患者台帳・保険資格・算定・請求確定の管理元とする。各アプリは自分のSQLite、職員認証、公式マスターを使い、連携設定が無効でも単独で動作する。

### 送受信の流れ

1. DENCALでカルテを確定し、請求対象の診療行為に実施日・数量・単位を記録する。送信権限のある職員が受診と送信内容を確認して **RECEPTへ送信** を選ぶ。
2. DENCALは送信待ちの内容をSQLiteに保存する。サーバー間APIで送信し、RECEPTが受信レコードをコミットしてから受領結果を返す。通信断があっても、カルテの確定状態は診療側に残る。
3. RECEPTの担当者が患者・資格・マスター・明細の差分を確認し、承認した内容を請求下書きに反映する。その後はRECEPTの算定・点検・請求確定の手順を使う。
4. DENCALの送信履歴は、RECEPTの状態照会APIから **受信済み／確認待ち／反映済み／拒否** を取得する。受領を請求下書きへの反映や請求確定の完了と混同しない。

### データ項目

| 区分 | v1で渡す項目 |
| --- | --- |
| 識別 | スキーマ版、連携ID、医療機関ID、送信元ID、DENCAL患者ID、受診ID |
| 版 | カルテ確定版番号、受診単位の連携版番号、元の連携版、送信種別（初回・訂正・受診取消）、訂正・取消理由 |
| 受診・傷病名 | 受診日、傷病明細の安定ID、傷病名コード・コード体系、開始日、疑い区分、主傷病区分、転帰 |
| 実施明細 | 実施明細の安定ID、診療行為コード・コード体系、実施日、数量、単位、状態（実施済み・取消） |
| マスター | DENCALが参照したマスターの種別・公表日など、特定可能な出典情報 |

患者IDの突合は `医療機関ID＋送信元ID＋DENCAL患者ID` を使う。初回の紐付けはRECEPT側で職員が確認する。名前だけの自動突合は行わず、既存台帳に患者がいない場合は登録と紐付けを確認してから反映する。保険証記号番号・公費情報はRECEPT側で登録・確認する。

受信側のマスター照合にはコード体系と適用日を使う。DENCAL側のマスター行IDはアプリ間の識別子として扱わない。SOAP本文、検査結果、紹介状、署名証跡、診療側の試算金額は送信項目に含めない。JSON Schema・HTTPステータス・エラーコード・テストデータは[共通の連携仕様 v1](../integration/recept-v1/README.md)を参照する。

### 再送・訂正・復元

- 再送では保存済みの連携IDとUTF-8 JSON本文をそのまま使う。RECEPTは送信元と連携IDで受信を一意に管理する。同じID・同じ本文ハッシュには既存の受領結果を返し、同じID・異なる本文は競合として保留する。
- カルテ版と連携版は独立して管理する。実施日の訂正や取消だけでも連携版を進められる。訂正版は受診単位の明細一式と取消状態を持ち、受信順が逆転した場合は先行版の確認まで保留する。
- RECEPTは前回反映した同じ受診の連携由来データとの差分を表示する。手入力や別受診のデータは保持する。確定済み請求に影響する場合は訂正候補として扱い、旧確定版を保持する。
- 片側をバックアップから復元した場合は、連携ID・版・本文ハッシュを照合し、未受領分を再送する。版の逆行や同じIDの本文不一致は手動確認とする。両側の記録を照合してから送信を再開する。

### 権限・通信・監査

初期構成の連携APIはループバックのサーバー間通信で使い、送信元・施設に紐付く専用認証を使う。職員操作には各アプリの認証を適用し、DENCALは対象受診の担当部署と送信権限、RECEPTは受信確認・紐付け・反映の権限を検査する。認証情報をブラウザーに渡さず、監査には連携ID・職員または送信元・時刻・結果を記録する。ログに連携本文や認証情報を記録しない。別ホスト間の配備はTLS・接続先認証・運用の設計後に検討する。

## 実装順序と受入条件

| 順序 | 担当 | 完了条件 |
| --- | --- | --- |
| 1. 連携仕様とテストデータ | 両方 | 実装済み。正常・重複・訂正・取消・未知コードを含む[共通テスト](../integration/recept-v1/README.md#検証と同期)を両方で実行できる。 |
| 2. 実施記録と送信待ち管理 | DENCAL | 実施日・数量・単位・取消を記録でき、確定済みの受診から送信データを生成して再起動後も再送できる。 |
| 3. 受信一覧と患者突合 | RECEPT | 同一送信を重複登録せず、未紐付けの患者・未知コード・未対応項目を保留できる。 |
| 4. 診療月別の下書き反映・訂正 | RECEPT | 対象月に固定点数の明細を反映でき、月またぎ、確定後の訂正・取消、手入力明細との共存を確認できる。 |
| 5. 結合テスト | 両方 | 外来1受診から請求確定まで通し、通信断、再送、同姓同名、別部署・別送信元、順序逆転、片側復元を検証する。 |

最初の到達点は、外来1受診の実施済み固定点数行為をRECEPTに取り込み、担当者が対象月の請求記録を確定できること。薬剤・材料、入院、オンライン資格確認、審査支払機関向けの正式な電子レセプト作成・送信は後続の対象とする。
